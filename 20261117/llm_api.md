# LLM Client

## LLM API란?

- 외부 언어모델에 요청을 주고 받는 인터페이스
- API = Application Programming Interface
- Client = 요청을 보내는 쪽 / Server = 요청을 받아 처리하는 쪽
- 강의 기준 FastAPI가 Client 입장에서는 Server, Open AI 입장에서는 Server가 됨.
  - Client <-> FastAPI <-> OpenAI

### SDK와 LLM Client의 차이점

- SDK: Software Development Kit
  - 소프트웨어 개발에 필요한 도구
  - 라이브러리/프레임워크 보다는 더욱 포괄적인 개념
  - 라이브러리와 프레임워크는 특정 기능 탑재에 집중한다면 SDK는 완전체와 가까움

### API 인증과 권한 구분

- API 키가 있다고 모든 권한이 있는 것은 아님 (주로 선정적/마약류/불법 해킹 등 범법행위에 대한 제약이 대표적임)
- Authentication: 인증 - 요청자격이 유효한지 확인
- Authorization: 권한 - 인증 시 사용했던 인증정보에 대한 권한 확인 (주로 모델 사용 범위, 잔액, 검열 등)
- ChatGPT 기준 구독제와 API 종량제는 구분해야 함 (단, 2026년 11월 17일 기준 Pro 요금제에 API 사용이 포함되어 있음)
- 모든 인증 정보는 .env 나 CI/CD를 통해 배포할 경우 별도의 Secrets 변수에 관리하는 등 보안 처리가 필요 (예시: Github Actions Secrets, AWS Secrets Manager, Azure Key Vault 등)

### Python 호출이 응답과 요청을 바뀌는 과정

- API를 요청하기 전 사용할 모델 지정, timeout, 재시도 횟수 등 예외처리 지정
- env 등 키가 있는지 확인
- SDK Client 초기화 / 요청 지시
  - SDK 객체 연결 (base url, timeout, max_retries 등)
  - SDK 응답 생성 (모델, Context/Prompt 등)

### 응답 객체에서 읽을 정보

해당 내용은 모두 관측/검증을 위해서 사용됨. 단, 모든 상황에서 매번 사용하는건 아님.  
응답 로그에서 JSON으로 관리 시 폴더 관리를 날짜가 아닌 요청 ID로 관리하는게 편리함. (예: response.request_id)
날짜로 관리할 경우 PC마다 시간대가 달라서 관리가 어려움

- response.id: OpenAI가 반환한 생성 응답 ID
- response.request_id: HTTP 요청을 추적하는 SDK 속성
- response.status: 응답 상태
- response.output_text: 텍스트를 모아 읽는 편의 속성
- response.usage: 관측된 토큰 사용량

### Instructions와 Input는 어떤 내용이 있는가?

- Instructions: 모델에게 지시하는 내용 (예: "다음 문장을 번역해줘")
- Input: 모델에게 지시하는 내용에 대한 입력값 (예: "Hello World")

### 선택한 지식만 요청에 포함됨

- 필요한 지식만 request에 전송됨
- 복합 질문(Query)에 대한 내용은 2026.11.17 기준으로 다루지 않을 예정. (복합 질문은 처리방식이 다름.)

## Structured Output

Schema 지정 -> API 생성 -> 로컬 검사 (규칙 등) -> 최종 사람 검토

- 응답을 임의의 구조로 저장해서 응답을 반환하는 과정
- 주로 JSON 형식으로 관리 (구조적이라면 yaml, xml 등으로도 관리할 수 있음)
- LLM에 JSON 형식으로 응답을 요청할 경우, 구체적인 형식 등 명시적으로 제시 해야함.

### WireAnswer와 KnowledgeAnswer는 역할이 다름 (강의 기준 임의로 생성한 객체임)

- WireAnswer: API 전송용 Schema 지정
- KnowledgeAnswer: 로컬 값 유효성 검증용 Schema (2026.11.16 수업에서 다룸)

### HTTP 상태, 생성 상태, 업무 상태 구분

- HTTP 상태: RFC9110으로 관리되는 HTTP 통신 규약에 대한 상태
- response.status: LLM에서 반환한 응답
- 답변 JSON의 status
  - 팀 내부 규약에 따라 다름
  - RAG/JSON 형식 예외 처리 등 검증 결과
- 응답이 가능한 상태인지 검증
  - 응답 내용이 맞는 형식인지 직접 검증
    - 가급적 if문으로 직접 검증
    - 프로그램 중단이 필요하다면 try/excpet 사용
  - Schema는 서버(FastAPI)에서 직접 지정한 형식으로 사용 (Pydantic 등)

## 스트리밍이란?

- 전체 응답이 끝날 때 까지 기다리는 대신 생성 중 도착하늩 텍스트 조각을 받는 방식
- Non-streaming: 전체 응답을 받을 때까지 기다리는 방식
- Streaming: 연결을 유지하며 이벤트를 순서대로 받고 완성된 내용부터 순차적으로 보여주는 방식

### SSE(Server-Sent Events)

- 서버가 클라이언트에 역으로 이벤트를 보내는 '단방향' 통신 방식

### Socket과 SSE의 차이점

| 구분        | Socket      | SSE         |
| ----------- | ----------- | ----------- |
| 통신 방식   | 양방향 통신 | 단방향 통신 |
| 프로토콜    | TCP 기반    | HTTP 기반   |
| 구현 난이도 | 복잡함      | 단순함      |

대부분 LLM 통신은 SSE만 사용해도 충분함 (Vision 이미지 포함)  
단, 음성 인식 등 실시간으로 통신이 필요한 경우 Socket을 사용하기도 함.

### Delta는 새로 도착한 텍스트 조각

- Delta는 변화분을 뜻함
- 버퍼에 누적함
- 토큰과 다른 개념임
- 불완전 종료 (json 포맷 오류, 사용자 임의 중단 둥) 시에는 성공처리 하면 안됨
- 텍스트 조각을 따로 모르고 상태에 따라 응답을 별도로 보관함 (이벤트가 도중에 끊겨서 응답이 깨지는 경우를 확인하기 위함)

### Latency 측정 기준

- Latency: 요청 시작 -> 결과 확인 까지의 지연. 측정시작과 종료시간을 지정해야 비교 가능
- Latency 측정 단위는 ms임
- Frist Text: 요청 시작부터 첫 비어 있지 않은 델타를 받은 시점
- TTFT: Time To First Token / 첫 토큰이 생성되는데 걸린 시간 (LLM 추론/성능 검증용)
- e2e: End to End / 요청 시작부터 최종 응답까지 걸린 시간 (예외처리 포함)

### Rate Limit 지정

- 일정 시간 동안 허용될 요청 수 / 토큰 사용량을 제한하는 정책
- RPM(Request Per Minute): 분당 요청 수 제한
- RPS(Request Per Second): 초당 요청 수 제한
- TPM(Token Per Minute): 분당 토큰 사용량 제한
- Open AI API의 RPM, TPM과 FastAPI 서버의 RPM, TPM은 별개임
- 계정/프로젝트/모델 별 실제 한도는 OpenAI 계정에서 확인

### HTTP 429의 상황별 예외처리

- 일시적 Rate Limit 초과: 대기 후 제한적 재전송 (남은 시간, 횟수, 최소 대기 시간 확인)
- 잔액, 할당량 문제/원인 불명: 중단 후 원인 확인 (재시도한다고 무조건 좋은건 아님.)

### 통신 재시도와 형식 수정은 별도 처리

- 재시도는 한번 더 보내는 동작이지만 왜 다시 보내느지 구분
- 통신 재시도: 일시적 제한이나 선별한 서버 오류 때문에 같은 생성 요청을 다시 보냄 / 전송횟수 증가
- 형식 수정: 응답은 받았지만 잘못된 형식일 때 수정 요청 / 새로운 생성 시도

### 생성 시도와 전송 홧수를 함께 제한

- 상황에 맞춰 규약 지정

## SDK 재시도와 앱 중 한 곳에서 재시도 관리

- SDK / 앱 재시도를 각각 제어하면 상정 외의 요청이 추가적으로 보내질 수 있음
- 이론 상 두 영역에서 관리하면 좋지만 실습 수준에서는 SDK에서만 관리해도 됨.
- 최대 횟수 이전 성공 시 조기 종료 / 최종 실패 시 응답 생성 실패로 전달

### Back off / Jitter의 필요성

- Exponential Back off: 제공된 대기 시간이 없을 때 실패가 반복될 수록 대기시간을 늘려 재시도하는 방식
- Jitter: 정확한 시점에 재시도 할 때 트래픽이 몰리는 것을 방지하기 위한 트래픽 조정 방법 / 주로 랜덤한 시간 간격을 두고 재시도
- Retry - After: 안내된 시간보다 일찍 전송하지 않음. 기다릴 시간이 부족하면 중단 처리

### Timeout

- 클라이언트에서 정한 요청 시간을 넘겨 응답 시도를 중단하는 것
- 중복 발생을 방지하기 위해 정책 지정 (예: timeout 발생 후 실패에 대한 내용을 기록)

## Token Usage / 비용 / Latency

- 측정 / 평가: 앱 내부에서 모든 전송의 사용량/시간/추정 비용 기록

### Token Usage = API가 보고한 사용량

- 문자 수나 수신 조각 수가 아닌 해당 호출의 usage 필드로 확인하는 입력/출력 토큰 정보
- 입력 안에 캐시 입력이 있음
  - Cached Tokens는 input tokens의 일부
- 출력 안에 추론 토큰이 있음
  - 해당 모델의 resoning_token은 output_token의 일부
- 캐시, 추론 토큰 등은 모두 임의로 총 입/출력 토큰에 더하지 않음

### 값을 못 받는 값과 실제 0을 구분

- 없는 사용량을 0으로 치환 했을 때 미확인 비용이 사라진 것 처럼 관측될 수 있음
- 비용에 대한 변조를 조심할 것

### None / 0 / not_run(미실행)은 모두 다른 의미를 가짐

- 타입 구분에 조심할것

### 한 작업 / 한 생성 / 한 전송 구분

- 기록은 "몇번 호출했는가" 외에 재요청 사유를 설명할 수 있어야 함

### source_mode는 결과를 얻은 방법

- 응답과 출처를 구분해야 시뮬레이션을 실제 성능으로 해석하지 않음
- api_live, simulated, app_cache, not_run 등 상태값 지정
- 상태값은 팀 내부마다 다름

### 마지막 성공을 기준으로 앞선 실패를 덮어 쓰지 않기

- 한 작업에 속한 기록은 모두 보존 / 알 수 없는 비용도 별도 계산
- 측정 비용 산정 시 입력 형식(text, image 등)에 따라 유동적으로 계산

### 출력 / 전송 / 전체 예산을 함께 검토

- 출력 상한: 한 응답의 생성 상한을 제한
- 작업별 상한: 최대 요청 횟수 이전에 완료 시 조기 종료
- 개인 호출 예산: 산정 시 캐시 무효화 후 호출 / 재시도에 대한 내용 포함

## Response / Prompt Caching

- 응답과 프롬프트를 빠르게 불러오기 위해 **임시로 저장** 하는 과정
- Cache Hit: 재사용 가능
- Cache Miss: 재사용 불가

### 캐시 사용 범위

- Response Cache: 검토된 최종 답변을 재사용 - LLM이 판단
- Prompt Caching: 같은 입력 앞부분의 계산을 재사용
- KV Cache: Key-value 상태를 재사용해서 앞선 Attention 계산을 반복하지 않도록 재사용 - 주로 Redis가 대표적임.

### Cache key에는 어떤 조건을 담는가?

- 같은 요청의 기준: 권한 범위 / 모델 / 질문 / 실제 문맥 / 설정 / 스키마 / validator / 버전을 포함
  - 같은 지식의 id여도 본문이 달라지면 다른 요청임
- SHA-256 / 식별용 해시: 입력 내용을 고정된 길이의 값으로 표현하는 해시 함수
- **Hash 값에는 암호 / API 키 / 개인 정보 등 민감 정보는 포함하면 안됨.**

### TTL

- Time To Live: 캐시를 저장하는 기간
- 만료 기준
  - 만료 시각
  - 만료 전에도 내부 속성 값 변경 시 만료됨

## Model Routing

- 요청 조건 / 권한 / 기능 / 예산에 맞는 모델 선택, 선택한 이유 기록
- 같은 요청 다른 후보: 예제로 Fast와 Quality라는 명시적 모드로 시작 - 해당 기준은 팀에서 임의로 만드는 정책임.
- 호출 전 선택과 Fallback
  - Routing은 호출 전 모델을 선택
  - Fallback은 실패 뒤 다른 대안으로 전환

### 실행 결과와 답변 객체 분리

- 클라이언트는 호출이 어떻게 끝났는지, 모델이 어떤 답변을 했는지 함께 반환
- 응답 json은 RDB에 보관
- 바뀌는 이유가 다른 책임을 분리
  - 폴더 수보다 호출 / 정책 / 검증 / 기록을 분리해 설명할 수 있는지가 중요
