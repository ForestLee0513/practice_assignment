# 심화 FastAPI 구현 흐름과 수정 기록

## 작업 범위

사용자가 작성한 Repository·Router의 H-API-01~10을 정리했습니다. 아직 작성하지 않은 `tests/test_contract.py`의 H-API-11~12는 그대로 유지했습니다. PostgreSQL 실습은 변경하지 않았습니다.

## 요청 처리 흐름

요청 → Router → Pydantic 입력 검증 → Repository의 JSON 조회·변경 → 응답 반환 순서입니다. GET·DELETE처럼 본문 모델이 없는 요청에는 본문 검증 단계가 없습니다. Router는 HTTP 응답을, Repository는 데이터 처리를 담당합니다.

### 목록과 상세 조회

`list_entries`는 JSON의 entries를 읽고 category가 None이 아닐 때만 완전 일치로 필터링합니다. 빈 문자열도 필터 조건이며 대소문자를 바꾸지 않습니다. 전체 목록과 필터 목록 모두 id 오름차순으로 정렬합니다. `itemgetter("id")`는 정렬 기준 값을 추출하며, 이 실습에서 성능 우위를 검증한 것은 아닙니다.

`find_entry`는 `next((조건에 맞는 항목), None)`으로 첫 일치 항목 또는 None을 반환합니다. Router는 항목이 없으면 404, 있으면 해당 JSON 객체를 반환합니다. 빈 목록은 404가 아니라 200과 빈 배열입니다.

### 생성

입력 모델의 `model_dump()` 결과를 Repository에 전달합니다. 입력 dict를 복사해 next_id를 id로 넣고 entries에 추가한 뒤 next_id를 1 증가시켜 저장합니다. 저장이 끝나면 생성한 항목을 반환하고 Router가 201과 그 항목을 응답합니다.

201을 선언하는 것만으로 파일이 저장되지는 않습니다. `write_data`가 성공해야 정상 결과를 반환합니다. 파일 누락·손상·쓰기 실패를 잘못된 요청으로 바꾸거나 빈 데이터로 숨기지 않습니다.

### 수정

PUT은 title·content·category를 모두 받습니다. `enumerate`로 대상 ID의 위치를 찾고, 없으면 None을 반환합니다. 대상이 있으면 입력 복사본에 기존 ID를 유지해 해당 위치만 교체하고 저장합니다. 항목 수와 next_id는 변하지 않습니다. 성공은 200과 수정 항목, 없는 ID는 404입니다.

### 삭제

Repository는 대상이 없으면 False를 반환하고 저장하지 않습니다. 대상이 있으면 항목을 제거하고 저장한 뒤 True를 반환합니다. next_id는 줄이지 않습니다. Router는 False에 404, 성공에 본문 없는 204를 반환합니다.

파일 읽기·변경·저장은 제공된 Lock 안에서 수행합니다. 저장 보조 함수는 임시 파일을 완성한 뒤 원본과 교체합니다. 이 구조는 단일 프로세스용이며 DB 트랜잭션이나 다중 프로세스 잠금을 제공하지는 않습니다.

## 오류 메시지와 응답 수정

| 상황 | 맞춘 응답 | 수정 이유 |
|---|---|---|
| GET·PUT·DELETE의 없는 ID | 404, `{"detail":"Knowledge not found"}` | 명세와 expected/404.json의 문구로 통일 |
| POST 성공 | 201과 생성한 지식 객체 | 기존의 빈 Response는 생성 ID와 응답 모델을 전달하지 못함 |
| DELETE 성공 | 204, 빈 본문 | 기존의 명시적 201 Response가 경로의 204 선언을 덮어씀 |
| 잘못된 요청 본문·경로 자료형 | FastAPI 기본 422 | Router에서 임의의 손상 메시지를 만드는 상황이 아님 |

기존 POST의 `Knowledge is not valid. Check data is curroupted.` 분기는 제거했습니다. Repository의 create는 저장한 dict를 반환하며, 저장 실패는 예외로 전파됩니다. 파일 손상을 422로 분류하지 않습니다. 422의 detail은 검증 오류 목록이며 문장 전체보다 오류 위치와 규칙을 확인합니다.

목록 조회에서는 category가 없는 경우도 정렬하도록 수정했습니다. 저장 순서가 현재 ID 순서여도 명세의 정렬 조건은 코드에서 보장해야 합니다.

## 작업 데이터 상태

현재 `data/knowledge.json`은 기존 id 1~3의 항목을 유지하며 next_id는 6입니다. 작업 전 커밋의 next_id 4와 달라졌지만 실제 수동 요청 로그가 없으므로 그 변화의 구체적인 원인을 단정하지 않습니다. 삭제 후에도 next_id를 줄이지 않는 계약에 맞게 현재 작업 상태를 보존했습니다. 원본 데이터를 초기화하지 않았습니다.

- 별도 임시 JSON의 저장 순서를 뒤집고 전체 목록 `[1, 2, 3]`, learning 목록 `[1, 3]` 정렬을 확인했습니다.
