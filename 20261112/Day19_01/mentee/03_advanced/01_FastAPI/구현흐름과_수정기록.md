# 심화 FastAPI 구현 흐름과 수정 기록

## 작업 범위

사용자가 작성한 Repository·Router의 H-API-01~10과 `tests/test_contract.py`의 H-API-11~12를 정리했습니다. PostgreSQL 실습은 변경하지 않았습니다. 실습 JSON 데이터는 커밋 대상에서 제외합니다.

## 요청 처리 흐름

요청 → 경로 선택과 Pydantic 입력 검증 → Router 함수 → Repository의 JSON 조회·변경 → 응답 반환 순서입니다. 잘못된 입력은 Router 함수가 실행되기 전에 422로 거부됩니다. GET·DELETE처럼 본문 모델이 없는 요청에는 본문 검증 단계가 없습니다. Router는 HTTP 응답을, Repository는 데이터 처리를 담당합니다.

### 목록과 상세 조회

`list_entries`는 JSON의 entries를 읽고 category가 None이 아닐 때만 완전 일치로 필터링합니다. 빈 문자열도 필터 조건이며 대소문자를 바꾸지 않습니다. 전체 목록과 필터 목록 모두 id 오름차순으로 정렬합니다. `itemgetter("id")`는 정렬 기준 값을 추출하며, 이 실습에서 성능 우위를 검증한 것은 아닙니다.

`find_entry`는 `next((조건에 맞는 항목), None)`으로 첫 일치 항목 또는 None을 반환합니다. Router는 항목이 없으면 404, 있으면 해당 JSON 객체를 반환합니다. 빈 목록은 404가 아니라 200과 빈 배열입니다.

### 생성

입력 모델의 `model_dump()` 결과를 Repository에 전달합니다. 입력 dict를 복사해 next_id를 id로 넣고 entries에 추가한 뒤 next_id를 1 증가시켜 저장합니다. 저장이 끝나면 생성한 항목을 반환하고 Router가 201과 그 항목을 응답합니다.

201을 선언하는 것만으로 파일이 저장되지는 않습니다. `write_data`가 성공해야 정상 결과를 반환합니다. 파일 누락·손상·쓰기 실패를 잘못된 요청으로 바꾸거나 빈 데이터로 숨기지 않습니다.

### 수정

PUT은 title·content·category를 모두 받습니다. `enumerate`로 대상 ID의 위치를 찾고, 없으면 None을 반환합니다. 대상이 있으면 입력 복사본에 기존 ID를 유지해 해당 위치만 교체하고 저장합니다. 항목 수와 next_id는 변하지 않습니다. 성공은 200과 수정 항목, 없는 ID는 404입니다.

### 삭제

Repository는 대상이 없으면 False를 반환하고 저장하지 않습니다. 대상이 있으면 항목을 제거하고 저장한 뒤 True를 반환합니다. next_id는 줄이지 않습니다. Router는 False에 404, 성공에 본문 없는 204를 반환합니다.

파일 읽기·변경·저장은 제공된 Lock 안에서 수행합니다. 저장 보조 함수는 임시 파일을 완성한 뒤 원본과 교체합니다. 이 구조는 단일 프로세스용이며 DB 트랜잭션이나 다중 프로세스 잠금을 제공하지는 않습니다.

## 오류 메시지와 응답 수정

| 상황 | 맞춘 응답 | 수정 이유 |
|---|---|---|
| GET·PUT·DELETE의 없는 ID | 404, `{"detail":"Knowledge not found"}` | 명세와 expected/404.json의 문구로 통일 |
| POST 성공 | 201과 생성한 지식 객체 | 기존의 빈 Response는 생성 ID와 응답 모델을 전달하지 못함 |
| DELETE 성공 | 204, 빈 본문 | 기존의 명시적 201 Response가 경로의 204 선언을 덮어씀 |
| 잘못된 요청 본문·경로 자료형 | FastAPI 기본 422 | Router에서 임의의 손상 메시지를 만드는 상황이 아님 |

기존 POST의 `Knowledge is not valid. Check data is curroupted.` 분기는 제거했습니다. Repository의 create는 저장한 dict를 반환하며, 저장 실패는 예외로 전파됩니다. 파일 손상을 422로 분류하지 않습니다. 422의 detail은 검증 오류 목록이며 문장 전체보다 오류 위치와 규칙을 확인합니다.

목록 조회에서는 category가 없는 경우도 정렬하도록 수정했습니다. 저장 순서가 현재 ID 순서여도 명세의 정렬 조건은 코드에서 보장해야 합니다.

## 작업 데이터 상태

실습 중 변경한 `data/knowledge.json`은 로컬 작업 상태로 유지하며 커밋하지 않습니다. 삭제 후에도 next_id를 줄이지 않는 계약을 따릅니다. 테스트는 별도의 임시 JSON을 사용하고 원본 데이터를 초기화하지 않습니다.

## H-API-11: 잘못된 입력과 파일 보존 검사

fixture의 `isolated`는 임시 저장 파일과 그 파일을 사용하는 TestClient를 제공합니다. 요청 전 `data_file.read_bytes()`를 before에 저장하고 빈 content로 POST한 뒤 다음을 검사합니다.

```python
assert response.status_code == 422
assert data_file.read_bytes() == before
```

첫 검사는 입력 거부, 두 번째는 entries와 next_id를 포함한 저장 파일 전체의 보존을 확인합니다. `response.content`는 HTTP 응답 본문인 bytes이고 `data_file`은 저장 파일의 Path입니다. 따라서 파일 보존 검사는 `response.content.read_bytes()`가 아니라 `data_file.read_bytes()`로 해야 합니다. bytes에 read_bytes를 호출하면 AttributeError가 발생합니다.

## H-API-12: 삭제 응답과 실제 삭제 검사

POST의 201을 확인하고 반환된 실제 ID로 DELETE한 뒤 세 가지를 검사합니다.

```python
assert response.status_code == 204
assert response.content == b""
assert client.get(f"/api/knowledge/{created_id}").status_code == 404
```

각각 삭제 성공 상태, 응답 본문 없음, 삭제 후 상세 조회 불가를 확인합니다. `b""`는 빈 bytes입니다. 비교에는 `==`를 사용하며 `assert response.content = b""`는 SyntaxError입니다.

마지막 줄의 assert를 생략하면 비교 결과가 False여도 테스트가 실패하지 않습니다. 두 번째 DELETE의 404는 중복 삭제를 검사하는 별도 사례이므로, 이 과제에서는 요구한 GET 재조회로 확인합니다. 테스트가 통과해도 작성한 검사가 빠져 있다면 요구사항 전체를 검증했다고 볼 수 없습니다.

## 검증

- 제공된 `python check_api.py`: 임시 복사본에서 60개 확인 통과. CRUD 응답·404·422·입력 길이·실제 JSON 보존 등을 검사합니다.
- 별도 임시 JSON의 저장 순서를 뒤집고 전체 목록 `[1, 2, 3]`, learning 목록 `[1, 3]` 정렬을 확인했습니다.
- 위 검증은 원본 JSON을 변경하지 않았습니다. 실제 서버 종료·재시작은 검증하지 않았습니다.
- `python -m pytest -q`: H-API-11·12 테스트 2개 통과. 파일 보존, 204·빈 본문, 삭제 후 GET 404를 확인했습니다.
- 실행 중 httpx 관련 StarletteDeprecationWarning 1개가 표시됐지만 테스트 실패는 없었습니다. 이 작업에서는 의존성을 변경하지 않았습니다.
