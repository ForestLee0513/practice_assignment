# FastAPI · SQLAlchemy CRUD 학습 정리

작성일: 2026-11-12

이 문서는 이번 대화에서 확인한 오류 원인과 해결 방법, 현재 코드의 구현 상태를 정리한다. 실제 DB 요청 테스트 결과를 별도로 검증한 문서는 아니다.

## 1. 요청 처리 구조

```text
HTTP 요청 → Router → Service → Repository → DB
HTTP 응답 ← 응답 모델 변환 ← Service 결과
```

- Router: 요청을 받고 Service를 호출하며, 결과를 응답 모델로 변환한다.
- Service: 존재 여부 확인과 업무 흐름, 트랜잭션 경계를 담당한다.
- Repository: 조회, 객체 추가 및 삭제 같은 DB 접근을 담당한다.

`KnowledgeWrite`는 title, content, category를 받고, `KnowledgeRead`는 여기에 id를 추가한다. Router의 `to_read()`는 ORM 객체의 `category.name`을 응답의 category 문자열로 변환한다.

## 2. POST에서 print 후 ResponseValidationError 발생

당시 코드는 `response_model=KnowledgeRead`를 지정했지만 `print(payload)`만 실행하고 반환하지 않았다.

```python
def create_knowledge(payload: KnowledgeWrite, db: Session = Depends(get_db)):
    print(payload)
```

Python 함수는 return이 없으면 None을 반환한다. FastAPI가 이 반환값을 KnowledgeRead로 검증하면서 오류가 발생했다.

```text
loc: ('response',)
input: None
```

이 오류는 DB 조회 오류가 아니라 응답 형식 검증 오류다. print 자체는 실행된 뒤에도 응답 검증은 실패할 수 있다.

현재 Router는 Service 결과를 반환하도록 구현되어 있다.

```python
result = service.create_knowledge(db, payload)
return to_read(result)
```

출력만 임시 확인할 경우에는 응답 모델을 제거하고 간단한 dict를 반환할 수 있다. 실제 CRUD에서는 응답 모델에 맞는 데이터를 반환한다.

## 3. POST ID는 증가하지만 GET에는 기존 3개만 조회된 이유

당시 생성 Service에는 `flush()`만 있었고 `commit()`이 없었다. GET Repository에는 3개로 제한하는 limit 코드가 없었다.

`flush()`로 INSERT가 실행되면 자동 생성 ID를 받을 수 있다. 하지만 commit하지 않고 세션이 닫히면 미확정 변경은 롤백된다. PostgreSQL의 시퀀스 번호는 롤백으로 되돌아가지 않으므로 ID는 증가하면서 실제 데이터는 남지 않을 수 있다.

따라서 ID 증가만으로 저장 성공을 판단할 수 없다. 롤백된 데이터는 다시 POST해야 하며, ID 사이에 빈 번호가 생길 수 있다.

## 4. add, flush, commit, rollback의 차이

| 작업 | 의미 |
| --- | --- |
| `db.add(item)` | 새 객체를 Session에 등록한다. 이 호출 자체로 INSERT가 실행되는 것은 아니다. |
| `db.flush()` | 대기 중인 변경을 SQL로 DB에 반영한다. 트랜잭션은 확정하지 않는다. |
| `db.commit()` | 자동으로 flush를 실행하고 트랜잭션을 확정한다. |
| `db.rollback()` | 현재 트랜잭션의 미확정 변경을 취소한다. |

커밋 전에 새 객체의 ID가 필요하면 명시적으로 flush한다.

```python
db.add(item)
db.flush()
print(item.id)
```

이 프로젝트의 Session은 `autoflush=False`이므로 일반 조회 전에 자동 flush가 수행될 것이라고 가정하면 안 된다. commit 시의 flush는 이 설정과 관계없이 수행된다.

## 5. transaction(db)가 commit을 대신 수행

`app/db.py`에 정의된 컨텍스트 매니저는 다음 구조다.

```python
@contextmanager
def transaction(db: Session):
    try:
        yield
        db.commit()
    except Exception:
        db.rollback()
        raise
```

`with transaction(db):` 블록이 정상 종료하면 commit하고, 예외가 나면 rollback 후 예외를 다시 전달한다. 따라서 블록 안에 commit을 중복으로 작성할 필요가 없다.

현재 create 코드는 with 블록 종료 시 commit한 뒤 생성된 ID로 재조회한다. 블록 밖의 불필요한 flush는 제거했다. 커밋 전에 ID를 사용하려면 flush를 블록 안에 둔다.

다음은 정리한 생성 코드 예시다. 이 문서를 작성하면서 소스 코드는 수정하지 않았다.

```python
def create_knowledge(db: Session, payload: KnowledgeWrite):
    with transaction(db):
        category = repo.get_or_create_category(db, payload.category)
        item = repo.add_knowledge(
            db,
            title=payload.title,
            content=payload.content,
            category_id=category.id,
        )
        db.flush()

    return get_knowledge(db, item.id)
```

분류 생성과 지식 생성을 같은 트랜잭션에 묶으면 둘 중 하나가 실패했을 때 함께 취소할 수 있다.

## 6. 조회한 객체 업데이트

같은 Session에서 조회한 ORM 객체는 속성을 변경하면 SQLAlchemy가 변경을 추적한다. 새 객체처럼 add를 다시 호출할 필요가 없다.

```python
def update_knowledge(db: Session, knowledge_id: int, payload: KnowledgeWrite):
    with transaction(db):
        target = get_knowledge(db, knowledge_id)
        category = repo.get_or_create_category(db, payload.category)

        target.title = payload.title
        target.content = payload.content
        target.category = category

    return target
```

`target.category = category`는 ORM 관계 속성에 Category 객체를 연결하는 방식이다. 블록 종료 시 flush와 commit을 거쳐 수정 사항이 저장된다. 중간 DB 반영 결과가 필요하지 않다면 명시적인 flush는 필요 없다.

현재 소스도 대상을 먼저 조회하고 존재 여부를 검증한 다음 분류를 처리하도록 수정했다. 사용자가 PUT 후 동작 확인을 완료했다.

## 7. 삭제 처리

현재 삭제 Service는 대상을 조회하고, 없으면 예외를 발생시키며, 있으면 같은 트랜잭션에서 삭제한다.

```python
with transaction(db):
    target = repo.get_knowledge(db, knowledge_id)
    if target is None:
        raise KnowledgeNotFoundError(knowledge_id)
    db.delete(target)
```

Router는 삭제 성공 시 본문 없는 `204 No Content` 응답을 반환한다. Service가 반환한 삭제 객체는 현재 Router에서 사용하지 않는다.

## 8. Truthy / Falsy와 None 검사

JavaScript에서 사용하던 `if (target)` 패턴은 Python에서 `if target:`으로 작성한다.

```python
if target:
    print("값이 있음")

if not target:
    print("Falsy 값")
```

| 검사 | 의미 |
| --- | --- |
| `if target:` | 참으로 평가되는 값인지 검사한다. |
| `if not target:` | 거짓으로 평가되는 값인지 검사한다. |
| `if target is None:` | 정확히 None인지 검사한다. |
| `isinstance(target, Knowledge)` | Knowledge 타입의 인스턴스인지 검사한다. |

Python에서는 None, False, 숫자 0, 빈 문자열, 빈 리스트, 빈 딕셔너리 등이 Falsy다. 특히 JavaScript와 달리 빈 리스트와 빈 딕셔너리도 Falsy라는 점에 주의한다. 사용자 정의 객체는 `__bool__` 또는 `__len__` 구현에 따라 진릿값이 달라질 수도 있다.

현재처럼 일반적인 ORM 객체 또는 None이 반환되는 조회에서는 `if not target:`을 사용할 수 있다. 다만 조회 실패를 뜻하는 None만 정확히 검사하려면 다음 표현이 더 명확하다.

```python
if target is None:
    raise KnowledgeNotFoundError(knowledge_id)

return target
```

이렇게 실패 조건을 먼저 처리하면 `is not` 없이 정상 흐름을 이어갈 수 있다. isinstance는 타입을 확인할 때 사용하며, 조회 결과 존재 여부를 확인하기 위해 반드시 필요한 검사는 아니다.

## 9. 현재 코드 확인 상태와 후속 확인

- POST Router는 Service 결과를 `to_read()`로 변환해 반환한다.
- 생성·수정·삭제 Service에 `transaction(db)`가 적용되어 있다.
- 목록 조회는 전체 결과를 반환하며 category가 전달되면 분류 조건을 적용한다.
- 생성 Service의 with 블록 밖 flush 제거를 완료했다.
- 수정 Service는 대상 존재 확인을 분류 처리보다 먼저 수행하며, 사용자가 H10 동작 확인을 완료했다.
- 실제 동작은 POST 후 별도 GET, PUT 후 GET, DELETE 후 GET으로 저장·수정·삭제 결과를 확인한다.
- 없는 ID에 대한 응답과 DB 제약 위반 시 동작은 별도로 확인해야 한다. 이 문서 작성 과정에서는 서버나 DB에 요청을 보내지 않았다.
